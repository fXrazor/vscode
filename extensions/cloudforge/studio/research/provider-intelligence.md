## Terraform Core: what the graph establishes

| Subject | Finding and consequence for Studio |
| --- | --- |
| Graph construction | Terraform builds graph nodes for resources, provider configurations and certain grouping/operation concerns. It adds explicit dependencies and expression references, incorporates state-only orphan resources, and validates cycles. A diagram with only resource cards cannot claim to reproduce the whole Terraform operation graph. [Dependency graph](https://developer.hashicorp.com/terraform/internals/graph) |
| Implicit dependency | An expression consuming another resource attribute establishes an ordering dependency. The expression may represent an attachment, ownership field, monitoring destination or simple value reuse. Preserve both the field meaning and the ordering facet. A copied location value is not a network attachment. [Resource dependencies](https://developer.hashicorp.com/terraform/language/resources/behavior#resource-dependencies) |
| Explicit `depends_on` | This handles otherwise hidden behavior dependencies; it does not establish communication or ownership. Whole-module dependencies can make plans more conservative. Studio needs exact source evidence before labelling a service edge explicit. [depends_on](https://developer.hashicorp.com/terraform/language/meta-arguments/depends_on) |
| Data sources | Reads normally occur during planning but may be deferred until apply when their inputs are unknown or dependencies change. A read is not a managed-resource create. Show a data/read mode when the source model supplies it. [Data sources](https://developer.hashicorp.com/terraform/language/data-sources) |
| Providers and aliases | Resource execution requires its provider configuration. Child modules receive provider configurations through inheritance or explicit mapping; alias configuration is not a region inferred from a diagram box. Provider configuration nodes and exact module/provider identity require a source adapter. [Providers within modules](https://developer.hashicorp.com/terraform/language/modules/develop/providers) |
| Modules and references | Module inputs and outputs propagate dependencies. A module is not a physical cloud boundary. Collapsing a module must retain boundary references; module-wide `depends_on` should not become an invented pairwise traffic mesh. [Modules](https://developer.hashicorp.com/terraform/language/block/module), [Outputs](https://developer.hashicorp.com/terraform/language/block/output) |
| State dependencies | State binds configuration to remote objects and retains information needed to operate on resources removed from configuration. A source-only canvas cannot see all destroy dependencies or resources outside its current model. [State purpose](https://developer.hashicorp.com/terraform/language/state/purpose) |
| Plan generation | Planning compares configuration, prior state and refresh results to propose actions. Unknown values and deferred reads matter. Proposed replacements belong to a particular plan and resource instance, not a blanket warning on every name field. [Plan](https://developer.hashicorp.com/terraform/cli/commands/plan), [Plan JSON](https://developer.hashicorp.com/terraform/internals/json-format) |
| Apply / destroy | Terraform walks dependencies with parallelism. Replacement can split an instance into create and destroy operations. Lifecycle settings such as `create_before_destroy` alter ordering and may expose naming constraints. Do not promise a universal exact apply timeline or simple reverse destroy order from this configuration view. [Graph](https://developer.hashicorp.com/terraform/internals/graph), [Lifecycle](https://developer.hashicorp.com/terraform/language/meta-arguments/lifecycle) |
| Graph command | `terraform graph` is a configuration/operation dependency rendering; graph type and saved plan affect the result. It is not a packet-flow or cloud-health map. No graph command was executed against a user's workspace in this research. [graph command](https://developer.hashicorp.com/terraform/cli/commands/graph) |
| Schema limitations | Provider schemas describe types, required/optional/computed access and nested blocks. They are not an exhaustive replacement/routing/security oracle. Version-matched docs, provider implementation and an authoritative plan provide additional evidence. [Provider schema command](https://developer.hashicorp.com/terraform/cli/commands/providers/schema) |

## Relationship contract

Every rendered relationship must have an instance-level reason. Registry rules only classify existing configured evidence; they must never connect all compatible resources. The semantic direction is **subject consumes, belongs to, or is associated with object**. The dependency arrow displayed in the canvas follows **prerequisite → consumer**, with the legend stating that direction. One relationship can have a category plus an execution-order facet; it is not duplicated into multiple indistinguishable lines.

| Category | Required evidence | What it does not prove |
| --- | --- | --- |
| Ownership | A documented ownership field referencing its owner, or actual observed ownership metadata | `parentId` alone: Studio uses it as an inheritance path; visual frame membership is presentation |
| Attachment | Documented association field and actual referenced endpoint; association resources retain their own identity | Network reachability, healthy targets or successful permission checks |
| Execution dependency | Actual expression binding, exact source `depends_on`, or a plan/graph edge with that provenance | Traffic or availability impact |
| Reference | Actual value expression, data lookup, module/output reference | Physical attachment; a location expression is value reuse |
| Runtime communication | Explicit configured routing/selector/backend intent, with separate confidence for observed endpoints/flows | A compatible service pair, proximity, names or a generic design line |
| Observability | Explicit collection/diagnostic/agent rule and destination reference | Healthy ingestion or collection from every adjacent workload |

The current bridge supplies resources, source summaries, typed field references where supported and opaque service edge kinds. It does not supply an authoritative plan, state graph, IAM evaluation, packet traces or Kubernetes status. Opaque edges must retain their origin/kind and remain unclassified where their semantics are unavailable. A user design connector remains diagram intent. A configured-dependent traversal is labelled **configured impact**, never operational blast radius; transitive dependencies are not proof that every dependent will fail or be replaced.

## Azure findings

Resource groups provide Azure management scope. VNets are network boundaries and subnets are child resources of a VNet. A VM drawn inside a subnet is not thereby attached to it: its NIC IDs and each NIC's IP configuration carry the network attachment. Studio's visual containment and provider inheritance stay separate. See the pinned `resource_group`, `virtual_network`, `subnet`, `linux_virtual_machine` and `network_interface` documents in the inventory below.

An NSG can filter a subnet or NIC via the corresponding association; an unassociated NSG does not protect nearby resources. Effective rules at both layers matter. Route tables similarly need an association; a next-hop address alone does not establish firewall readiness, reciprocal routing or reachability. Public IPs need a NIC/frontend association. Load balancer pools and NIC pool associations preserve the intermediate registration object. Application Gateway has dedicated subnet, listener, backend, probe and certificate constraints. Azure Firewall needs compatible subnet/addressing plus actual routing through it. [NSG design](https://learn.microsoft.com/azure/networking/design-guide/network-application-security-groups), [VNet/subnet design](https://learn.microsoft.com/azure/networking/design-guide/vnets-subnets), [Application Gateway infrastructure](https://learn.microsoft.com/azure/application-gateway/configuration-infrastructure)

AKS subnet placement, network plugin/IP capacity, identity, egress and monitoring integrations have different dependencies. An identity assignment is not a role grant and permission propagation can delay a deployment. Storage and Key Vault data-plane access also depend on network policy, private DNS and principal grants; management-plane success does not establish secret/blob access. Log Analytics is a destination. Guest VM telemetry needs the applicable agent, data collection rule and association; diagnostic settings are a different collection path. [AKS network practices](https://learn.microsoft.com/azure/aks/operator-best-practices-network), [VM collection](https://learn.microsoft.com/azure/azure-monitor/vm/data-collection), [Data collection rules](https://learn.microsoft.com/azure/azure-monitor/data-collection/data-collection-rule-overview)

Hub/spoke recognition requires actual local/remote peering endpoints and their direction. It must not be inferred from labels. Peerings are nontransitive; a shared firewall path also needs relevant routes/next hops. A layout may put a well-evidenced hub centrally, but it cannot assert transit connectivity from the pattern. Common investigations include overlapping CIDRs, missing NSG/route associations, insufficient subnet capacity, identity permission/propagation, backend probes and private DNS. Separate association resources can prevent reciprocal inline-reference cycles. [Hub/spoke architecture](https://learn.microsoft.com/azure/architecture/networking/architecture/hub-spoke)

## AWS findings

A VPC contains zonal subnets. ENIs place workloads in subnets and associate security groups. Group-to-group rule references describe filtering, not group ownership or ENI attachment. Explicit route-table associations and the VPC main-table fallback determine effective subnet routes. A NAT gateway needs compatible subnet, routing and addressing; an internet gateway attachment alone does not give an instance internet access. [VPC resource map](https://docs.aws.amazon.com/vpc/latest/userguide/view-vpc-resource-map.html), [Subnet routes](https://docs.aws.amazon.com/vpc/latest/userguide/subnet-route-tables.html)

EC2 role use goes through an instance profile; role trust, permission policies and their attachment are distinct objects. EKS control-plane subnet/SG/role configuration differs from managed-node-group placement and its node role. Multi-AZ coverage, subnet capacity, API endpoint mode and worker egress are separate failure causes. ALB and NLB share `aws_lb` but listeners, actions, target groups/registration and health checks determine behavior. RDS uses a DB subnet group plus security groups and database-specific settings. [EKS subnet practices](https://docs.aws.amazon.com/eks/latest/best-practices/subnets.html)

S3 buckets are account/region services, not subnet children. Lambda's execution role differs from invocation permission; optional VPC ENIs can change internet access and require network/IAM prerequisites. CloudWatch logging requires execution-role grants. Route53 records belong to a zone and may reference a load balancer name, which is not proof of target health. Common failures include circular inline SG references, missing role policy readiness, incompatible ENI zone/index, unhealthy targets, absent egress and RDS deletion protection/snapshot requirements. [Lambda logging](https://docs.aws.amazon.com/lambda/latest/dg/monitoring-cloudwatchlogs.html)

An AWS landing zone includes account/OU boundaries, baseline identity, security and logging controls. Multiple VPCs or resource names do not establish it. Pattern rendering needs actual organizational and baseline configuration evidence; the current adapter cannot assert a complete landing zone. [Landing-zone design](https://docs.aws.amazon.com/prescriptive-guidance/latest/designing-control-tower-landing-zone/)

## Google Cloud findings

VPC networks are global; subnetworks and Cloud Router/NAT are regional; VM zones must match subnet regions. Cloud NAT is regional outbound translation configured through a Cloud Router, not a packet-forwarding VM or unsolicited inbound service. Firewall target tags/service accounts and IAM grants mean different things. A VM service-account attachment does not establish its API scopes or permissions. [VPC](https://docs.cloud.google.com/vpc/docs/vpc), [Subnets](https://docs.cloud.google.com/vpc/docs/subnets), [Routes](https://docs.cloud.google.com/vpc/docs/routes), [Cloud NAT](https://docs.cloud.google.com/nat/docs/overview)

GKE network/range/endpoint-isolation and workload-identity configuration require separate evidence. Cloud SQL private access needs the chosen private-services-access or Private Service Connect prerequisites; a VPC expression alone is incomplete. Cloud Storage has no subnet ownership. Project IAM member, binding and policy resources have different authority and can conflict when mixed for the same role. [GKE isolation](https://docs.cloud.google.com/kubernetes-engine/docs/concepts/network-isolation), [Private services access](https://docs.cloud.google.com/sql/docs/postgres/configure-private-services-access)

Load balancing is a chain of forwarding rule → compatible target proxy → URL map → backend service/group and health checks. Regional and global HTTP chains have separate Terraform types; the registry includes both. Other load-balancing schemes and proxy/target types remain unreviewed rather than guessed. Logging sinks require writer permissions at their destination. Metric filters in alert policies do not establish ownership or prove that a monitored resource is present in the diagram. Common failures include regional/global mismatch, unavailable service APIs, missing private-service networking, mismatched ranges and denied service-account/sink permissions. Exact field evidence is linked in the pinned inventory.

## Kubernetes findings

Namespaces scope namespaced objects but do not nest. PVs and StorageClasses are cluster-scoped. Controller ownership comes from ownerReferences, with Deployment → ReplicaSet → Pod differing from namespace scope. Services select Pods or refer to other endpoint arrangements; selector matches establish intent, not ownership, readiness or permitted traffic. EndpointSlices, network policies and observed status are additional evidence. Ingress requires a compatible controller/class and references Services and optional TLS Secrets. [Owners/dependents](https://kubernetes.io/docs/concepts/overview/working-with-objects/owners-dependents/), [Namespaces](https://kubernetes.io/docs/concepts/overview/working-with-objects/namespaces/), [Services](https://kubernetes.io/docs/concepts/services-networking/service/)

Pod ConfigMap/Secret inputs are references; graph analysis should collect names, not secret contents. Update/restart behavior differs for environment, volume and subPath use. StatefulSets combine stable identity, a governing Service and claim lifecycle. DaemonSets target eligible nodes, not every node without conditions. PVC/PV binding depends on class, capacity, access modes and topology; WaitForFirstConsumer can defer binding. Reclaim policy and finalizers affect removal. These are future adapter rules, not an implicit addition to the supported three cloud providers. [ConfigMaps](https://kubernetes.io/docs/concepts/configuration/configmap/), [Secrets](https://kubernetes.io/docs/concepts/configuration/secret/), [Persistent volumes](https://kubernetes.io/docs/concepts/storage/persistent-volumes/), [StatefulSets](https://kubernetes.io/docs/concepts/workloads/controllers/statefulset/), [DaemonSets](https://kubernetes.io/docs/concepts/workloads/controllers/daemonset/)

## Technical View design decision

Purpose: inspect effective configuration, explain why resources are related, trace configured dependencies and investigate local findings. Architecture Design View remains the diagram composition workflow. Switching views must not rewrite resource positions, Terraform or history.

The screenshot's overlap is caused by rendering wide/tall cards at the same compact icon positions. The first implementation will use a deterministic, bottom-up, size-aware spacing projection. Preserve visual container membership, pack siblings by documented layer with actual configured relationships as ordering evidence, and grow rendered containers around the result. Unknown types still receive collision-free space. Layer order is a navigation aid, not an invented networking → security → compute dependency chain. Do not force cyclic or reciprocal relationships into a fake DAG.

Automatic spacing is presentation state. Keep canonical architecture coordinates untouched when enabling it or switching modes. A manual drag in the projection is translated into the same canonical delta, so returning to Design shows the movement and Undo remains one semantic command. Keep projection offsets stable during manual moves; an explicit Space resources action can recompute them. New resources/container topology and changed measured dimensions can trigger a fresh projection. Provide a contextual View choice to return to design positions. No second editable architecture, per-mode configuration copy or layout operation enters semantic history.

Use actual measured card bounds with a bounded compact card design. The graph should lead to full shared Parameters/Code/Context, rather than display every form field on every card. Keep selected-neighborhood relationships visible by default, with a compact explanation of category, source field and prerequisite-to-consumer direction. Distinguish configured references from user design links. Expose configured downstream impact and investigation hints in contextual UI; mark missing plan/state/runtime evidence plainly. Reduce animation and disable it under reduced-motion preferences.

React Flow explicitly leaves automatic layout to the application. Its documented comparison notes Dagre's limitation with cross-boundary subflows; D3 force/hierarchy do not meet compound layout requirements. ELK supports dynamic compound layouts and routing but brings a larger asynchronous solver and integration complexity. For this bounded collision problem, choose a small deterministic compound packing projection first, with measured sizes and no dependency addition. Keep the layout interface replaceable if crossing minimization/orthogonal routing later justifies ELK. [React Flow layout guide](https://reactflow.dev/learn/layouting/layouting), [Measured nodes](https://reactflow.dev/api-reference/hooks/use-nodes-initialized)

Pattern rendering is conditional: actual peering relationships can suggest hub/spoke; actual region/provider identities can separate regions; actual cluster/subnet/identity relations can organize AKS/EKS. Do not assert patterns when required evidence is missing. This pass must not claim state/plan-driven ordering, live network troubleshooting, multi-region placement from fallback labels, universal replacement warnings, prices or operational blast-radius results.

Required verification: the user's 19-resource duplication/nesting case; zero sibling card overlaps and contained children after switching; stable repeated switch; theme/selection/form/source preservation; no architecture/history mutation from layout; shared drag delta and exact Undo; measured-size reflow; documented attachment versus reference classification; no links from proximity/type alone; unknown rules/version applicability; keyboard focus and reduced motion; both themes at 1360×860 and 1024×768. Existing connector/hosted refresh regressions must remain passing.
