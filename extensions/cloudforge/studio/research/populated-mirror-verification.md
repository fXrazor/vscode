## Findings and fixes

**Windows mirror publication failed beyond MAX_PATH.** The native archive flow accepted the verified ZIP but returned a generic workspace-unavailable error during publication. In the disposable service data directory, the package manifest destination was 262 characters. The Rust store passed plain paths to `MoveFileW`; a Windows regression reproduced OS error 3 before the fix. The fix canonicalizes the staged file and destination's existing parent into extended absolute paths while retaining the same no-overwrite API, checksum/ZIP checks, locks, rollback and leases. See the [Rust repair plan](C:/Users/dalep/.codex/worktrees/provider-mirror-long-paths/CloudForge/docs/superpowers/plans/2026-11-26-provider-mirror-long-paths.md).

**Missing Linux packages hid a valid local Windows initialization path.** The old manager used default Windows+Linux readiness to decide whether to show local Windows init. With the Windows package present and Linux absent, it showed the Windows package as ready but hid initialization. The manager now requests Windows-only readiness separately, labels both platform sets, and offers the existing initialization review when the validated Windows report permits it. It retains the dual-platform missing/corrupted rows. The new strict parser rejects mismatched workspace/architecture/revision, unexpected platforms, duplicate or malformed entries, inconsistent readiness, and oversized reports. A failed or incompatible Windows report displays unavailable rather than authorizing init.

This follows the existing [approved native workflow](../../../../docs/cloudforge/offline-provider-management-spec.md): default dual-platform readiness and Windows-only local init are separate facts. It adds a temporary native result row, without a new permanent panel or architecture state.
